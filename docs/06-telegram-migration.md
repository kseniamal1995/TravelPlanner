# План миграции в Telegram Mini App

## Фазы

| Фаза | Что | Статус |
|------|-----|--------|
| 0 | Прототип UI (этот репозиторий, schema v12) | ✅ |
| 1 — MVP TMA | Бот + хостинг + хранилище на пользователя + ручной ввод мест | ⏳ |
| 2 — Умный | Бэкенд: LLM-генерация маршрута + Places API + онбординг | ⏳ |
| 3 — Рост | Пуши по дедлайнам, шаринг, авто-еда, совместные поездки | ⏳ |

## Фаза 1 — инфраструктура

1. **Бот** через BotFather, регистрация Mini App с URL.
2. **Хостинг** статики: Vercel / Netlify.
3. **`telegram-web-app.js`**: тема (маппинг токенов на `themeParams`, см. 04), `initData`, MainButton («+ Добавить место» / «Сохранить» в шитах), BackButton (вместо «← Поездки»), haptics на чек-офф/undo/удаление, safe areas.
4. **Хранилище — адаптер** с одним интерфейсом:
   ```js
   storage = { async get(key), async set(key, value) }
   // реализации: artifact (текущая) → Telegram CloudStorage → REST API
   ```
   ⚠️ **Лимиты CloudStorage**: значение ≤ 4096 символов, ≤ 1024 ключей. Состояние поездки уже сейчас десятки КБ ⇒ CloudStorage только с чанкованием (`trip:{id}:0..n`) или сразу БД (Vercel Postgres, ключ = Telegram user id). Рекомендация: не тратить время на чанкование — фаза 1 с лёгким API + БД.
5. **Валидация `initData`** (подпись) на каждом запросе API — обязательна.

## Фаза 2 — умный движок

### Генерация маршрута
- Вход: город, даты, отель/район, темп ходьбы, **темы дней** (`day.theme` — UI уже собирает их в шите дня), интересы, must-see, фиксированные события (концерт с временем), время прилёта/вылета.
- LLM (Claude API) применяет правила «человеческого» маршрута (см. 01-product и `project-docs.md` §3.4) + **Places API** даёт рейтинги, координаты, часы работы, фото, ссылки.
- Выход — структуры из 03-data-model: `days[] + places[]` с `leg`, `sect` (части дня!), `ticket.lead` (дедлайны брони), `warnH/warnS`, `arrivalDay`-логистика. Прототип уже умеет всё это рендерить — движок должен заполнять те же поля.
- Эталон качества — seed Парижа. Сценарии-эвалы: день прилёта, день с якорем-событием, день отъезда, «чиллее», «добавь еду».
- Пересчёт остатка дня по чек-оффу `done` — кандидат фичи («я выбился из графика»).

### Замены прототипных решений
| Сейчас (прототип) | В продакшене |
|---|---|
| `wiki:` + Wikipedia REST фото | Google Places Photos (тот же интерфейс «url по месту») |
| `g(name+' Paris')` deep-links | геокодинг Places при добавлении места |
| `rname` руками | place_id из Places |
| захардкоженные подсказки (метро, билеты) | генерация по городу |
| Open-Meteo на клиенте | можно оставить как есть (бесплатно, без ключа) |

### Онбординг пользователя
Шаги: город → даты → отель/район → темп → интересы → must-see → фиксированные события. Ввод мест: Places autocomplete **или OCR скриншотов** (загрузка картинок → распознавание названий). Прямой импорт google-подборок невозможен (нет API).

## Фаза 3
- **Пуши**: бот шлёт сообщение по крайним датам напоминаний (`reminders[].due` уже есть).
- **Шаринг**: deeplink на поездку, совместное редактирование.
- **Авто-еда** под `city.food` и бюджет.

## Бэклог UI (не блокирует фазу 1)
- Bottom-sheet действий с местом (вместо «Изменить»: перенести/удалить/заметка) + drag-сортировка.
- «Копилка» — объединить под-вкладки идей в один список с чипами-фильтрами; прямое действие «+ в день» на карточке идеи.
- Бейджи `must` и `✨ совет` из существующих полей `pri`/`rec` (поля уже в данных).
- Тёмная тема через `themeParams`.
- Иллюстрированные пустые состояния (сейчас — иконка в круге).
- Погода в советах движка (дождь → крытые места).

## Риски
- **Стоимость API** (LLM + Places): лимиты, кэш справочных данных по городам.
- **Качество маршрутов**: нужны эвалы до открытия на пользователей.
- **Приватность**: данные поездок персональны; initData-валидация, без сторонней аналитики в MVP.
- **CloudStorage-лимиты** (см. выше) — не закладываться на него для основного состояния.
